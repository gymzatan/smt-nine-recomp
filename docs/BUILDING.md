# Building from your Japanese disc

## Requirements

- Windows 10/11 x64 and sufficient free disk space for the extracted disc, generated C, native build, language packages and high-resolution font atlases. Keep at least 15 GB free; 16 GB RAM or more is recommended.
- Python 3.14 x64, available through the Windows `py` launcher.
- Visual Studio 2022 Build Tools with Desktop development with C++, Windows SDK, CMake and Ninja. The scripts locate the installation using `vswhere`; no developer drive paths are required. A portable installation can be selected explicitly with `NINE_VS_ROOT` set to its Build Tools directory.
- [Rustup](https://rust-lang.org/tools/install/) installed and on PATH. The default Windows installer adds `%USERPROFILE%\.cargo\bin` to the user PATH; fully close and reopen the terminal or editor afterward, then verify `rustup --version`. `setup.cmd` installs the pinned Rust toolchain, not Rustup itself.
- For `--with-chinese` only: FFmpeg and FFprobe on PATH, with WMV2 encoding and the subtitles/libass filter enabled.
- For `--with-chinese` only: Windows Simplified Chinese supplemental fonts, `%WINDIR%\Fonts\simsun.ttc` and `%WINDIR%\Fonts\simhei.ttf`. Font files are not included in this project. Chinese glyph identities, encodings, layout and rendering rules are supplied by the repository. Japanese builds and English imports do not require these fonts or FFmpeg/FFprobe.
- Internet access for the declared Python, Cargo, DirectX Shader Compiler and WineD3D dependencies. Their origins and GPU archive layouts are recorded in `requirements.txt`, `Cargo.lock` and `config/dependencies.json`. Rerun `setup.cmd` after pulling changes to Python requirements; it installs the PE parser used for GPU dependency preparation.

## Supported input

Gameplay hardware requirements and the limits of current GPU/VRAM verification are listed in the [README](../README.md#system-requirements). The RAM/disk guidance above is for building.

The initial build accepts unmodified Japanese game data in a bare game-partition XISO (`.xiso.iso` or `.iso`) or a full-disc ISO dump containing the video partition. The existing XDVDFS reader automatically locates the game partition from its descriptor; no conversion or format option is needed. Use `build.cmd --iso "path to your image"` for either layout.

The whole-disc checksum is not an acceptance requirement: padding, sector arrangement and the video partition can differ. Every extracted game file is still checked against the complete 3,515-file manifest in `config/retail.json`; modified, missing, unexpected or repeated files fail explicitly. The original `default.xbe` SHA-256 is `6c249401369ed41c2a319762f0b56b80aefde3efe766ac0d8731889a4150deac`. Supply the image yourself; externally translated images use the separate Config import flow, which uses the same layout detection.

An already-extracted original Japanese folder is also accepted by the same option:

```bat
build.cmd --iso "D:\Games\NINE-original"
```

Select the folder containing `default.xbe` and `Media`, with the same complete original file set as the disc. The build checks all files before copying them into `data/japanese`; it does not edit the source folder. Modified or translated folders are not initial-build inputs. Source and destination folders must not overlap. Use a fresh checkout for the initial build, as with an ISO.

## Build

In a fresh checkout:

```bat
setup.cmd
build.cmd --iso "D:\Games\Shin Megami Tensei - Nine (Japan).iso"
```

`--jobs 4` is the default compiler parallelism. Resource preparation is sequential. CMake/Ninja and Cargo manage the dependency graph for compilation; object and crate outputs are independent.

The default pipeline extracts Japanese resources into `data/japanese`, prepares the Japanese runtime image and shared code-generation input, builds title assets, generates the game C from the pinned original lifter, applies the explicit project codegen edits, builds the DSP dependency, and compiles the existing host/runtime and Config. It does not create Chinese Media, high-resolution font atlases or subtitled movies.

To include Chinese, use this initial command instead:

```bat
build.cmd --iso "D:\Games\Shin Megami Tensei - Nine (Japan).iso" --with-chinese
```

This additionally creates `data/chinese/Media`, `runtime/fonts` and the Chinese runtime image through the existing text/font/subtitle writers. Both builds retain the same checked shared code-generation recipe, including its existing popup edits. In a Japanese-only build, the prepared code-generation image stays under `build/localization/native_codegen.xbe` and is not installed as a playable Chinese image. The source translation inputs used by that recipe remain in the repository; no Chinese system fonts or movie tools are needed for this step. The build does not use any development-directory XBE, generated C, Media, prebuilt DSP library, font atlas or game executable.

The existing project code-generation edits submit single-row and four-row shader constants, bound-resource index ranges and existing packed vertex-program resources as native operations through the original ordered queue. The same renderer constant, primitive and program storage consumes their raw values, preserving CPU shadow state, architectural registers, resource references, buffer extent, refill continuations and subsequent drawing order. Incompletely published operations remain pending through checkpoints. Packed program resources retain their original constructor, queue copy and upload blocks; bulk consumption calls the original word writer and preserves its decoded-instruction dirty flags, load cursor and completed register state. Hardware programmable batches collect the used-input mask during the original program-validation scan. The immediate flush reuses that batch's raw program pointer and length; nothing is cached across batches. Partial uploads, context-write rejection and the original decoded state and shader binding remain unchanged. No second shader cache or program-storage implementation is introduced. Other game-side graphics commands still use the existing Xbox command path. The graphics worker checks the original acquire-ready flag before entering its event wait. A pending request goes directly to the same ordered consumer and GPU progress checks; idle workers still wait on the original event. Device checkpoint barriers, lock ordering, notifications, shutdown and single-thread behavior are unchanged.

The hot matrix multiplication and transpose retain their original SSE sequences in one Windows x64 assembly module, assembled by the same MSVC toolchain. Their generated callers preserve guest registers, output writes and continuation handling. Built-in and imported languages use the same module. The shared x87 comparison helper evaluates each instruction operand once, including volatile game memory, and retains the original ordered/unordered result codes and status mapping. The existing project generator copies this same header into built-in and imported language output; animation scans, guest continuations and graphics progress are unchanged.

The native game and imported languages use the `Release` compiler configuration. MSVC optimizes the game and existing runtime libraries together with link-time optimization; floating-point rules and the CPU instruction target are unchanged. The resulting entry points are `Config.exe` and `smt9_recomp.exe` in the project root. Double-click either executable directly. The game opens without a console window. Runtime paths are resolved from the executable directory; keep `data`, `runtime` and `backends` beside the executables when moving the folder. No drive letter or launcher script is required. Defaults are an English interface and Japanese game; `--with-chinese` selects Chinese defaults instead. Existing saved settings remain in effect.

The Vulkan backend loads the system Vulkan driver directly and compiles the existing generated shaders to SPIR-V with DirectX Shader Compiler. It creates Vulkan images, pipelines, command buffers, timeline completion and the window swap chain without a D3D11 device or DXVK. It requires Vulkan 1.3, geometry shaders, precise occlusion queries, timeline semaphores, mirror-clamp sampling and dynamic rendering. The game still produces Xbox graphics commands; replacing that producer/consumer work remains separate from the native host API. The existing upload ring reuses byte-identical immutable constant ranges within their live generation; image barriers target the actual resource consumers. Upload capacity is checked before opening an idle command buffer, so moving past a full ring segment does not submit an empty batch. Recorded GPU work still submits normally, and the existing generation, descriptor reset, last-read wait and growth rules govern storage reuse. Vulkan drawing reads existing cached vertex rows and primitive indices as separate inputs. The original upload ring consumes them synchronously or reuses its still-live generation, avoiding a duplicate vertex copy and contiguous D3D staging pack. The original vertex decoder, cache identities, memory-write invalidation and checkpoint/shutdown lifetime remain authoritative; D3D consumers retain their required contiguous input. Complete 32-bit color clears are issued to the existing GPU surface without a duplicate CPU fill; the original completion boundary and physical memory owner remain. CPU reads and snapshots obtain the pixels through the existing guarded publication path. CPU readback buffers prefer a compatible host-cached Vulkan memory type; upload buffers retain their existing memory choice. Required visibility, memory-type compatibility, queue completion and noncoherent invalidation still apply. Color readbacks share one context-owned transfer buffer under the existing graphics lock. It grows only to the largest requested image and is released at graphics shutdown; every read still performs a fresh GPU copy, completion wait and visibility operation. Pixel contents are not cached. Partial clears and retained larger surfaces preserve untouched pixels. GPU completion remains tied to real queue completion. Color checkpoint metadata restores native-size surface identities before the first post-load presentation, using the already saved physical-memory pixels; only higher-resolution images need extra pixel payloads.

Polygon LINE and FILL states use the original face selection and host rasterizer on D3D11, D3D12, OpenGL and native Vulkan. Vulkan wireframe effects require the device’s `fillModeNonSolid` feature. Disabled vertex arrays consume the original current attribute registers, including the white diffuse color used by menu transitions; cached vertex rows include these register values in their identity. Swizzled offscreen render targets remain available to texture consumers and are excluded from linear display-buffer selection.

The default `Auto` graphics selection attempts Vulkan, OpenGL, D3D12, then system D3D11. D3D12 creates a native D3D12 device and command queue, then exposes the existing D3D11 rendering contract through Microsoft D3D11On12. It needs a D3D12-capable driver and is not assumed to reduce CPU or memory costs. Each implementation checks its own driver requirements. A failed DLL load, factory creation or device creation advances to the next backend. Partial device objects are released immediately; runtime DLLs load once and remain until process exit because unloading them can invalidate shared native-driver state even after another device is created. A manually selected backend is used exclusively. Errors after successful device initialization still stop explicitly; a driver crash or hang cannot return an initialization error to this loop.

Direct GUI launches write diagnostics to `runtime/startup.log`, including each graphics attempt, failure code and selected adapter/backend. If graphics initialization fails, an error dialog points to that log and Config. Launches with redirected standard error retain their existing output destination.

Graphics initialization requests a 1 ms Windows timer period for every backend and releases the paired request at process exit. Checkpoint-aware waits accept the original host timeout when the complete remaining interval has elapsed, instead of repeating that interval until a coarse tick counter advances. Checkpoint boundaries, saved remaining duration, object/APC results and infinite waits retain their original handling. Dependency preparation selects WineD3D's existing event-based command-thread wakeups instead of direct thread alerts, which can interfere with Windows lock waits. Both signaling and waiting use the same existing event; graphics threading remains enabled. Prepared backend files are tracked by the native build, so a dependency-only update also refreshes the DLLs beside each language executable. WineD3D polls completion events on a command thread; coarse host waits can stall the original per-glyph fences even at 1x resolution. GPU completion checks, game clocks, the selected 30/60 Hz rate and glyph rendering retain their existing behavior.

The game window presents a completed GPU surface through the selected backend's existing device and swap chain. The GPU applies the configured aspect ratio and black borders. Display submission shares the renderer's context lock. **Vertical synchronization (VSync)** is an independent Config checkbox, saved as `Display/VSync=0` or `1` in `runtime/NINE.ini`; missing settings default to off. Save and restart to apply. Off requests immediate presentation; on requests refresh-synchronized presentation. Vulkan selects IMMEDIATE or FIFO respectively; D3D11, D3D12 and WineD3D receive a DXGI sync interval of zero or one. Driver/compositor settings can still affect display scheduling. The game's 30/60 Hz setting continues to control simulation pacing independently. A requested Vulkan present mode that the surface does not support is reported explicitly. Screenshot and instant-state capture read back the completed image on demand. Flip acknowledgement still waits for real GPU completion.

Colour data stays on the GPU until the existing memory-ownership rules require CPU-visible pixels. A complete clear discards the overwritten pixels without reading them back; partial channel/rectangle clears and neighbouring surfaces on shared pages retain their untouched bytes. Texture binding publishes overlapping color data only when that surface has GPU writes. Pending completion outputs are checked through the existing physical texture and palette ranges; an output elsewhere does not force unrelated color readback. A CPU write guarded only by cached texture content invalidates that physical page without collecting unrelated outputs. Pages belonging to color surfaces or queued outputs keep their existing publication and completion requirements. Recently bound texture identities move to the front of the same lookup list; full identity matching, storage and shared-page invalidation remain unchanged. The existing clear writer, texture cache, native shaders and completion queue remain authoritative. Game-side Xbox command construction and consumption still run; direct GPU presentation does not remove those remaining CPU costs.

Chinese high-resolution font atlases use read-only file mappings. The existing texture cache reads the original pixels when a page is needed, without allocating a private copy of every atlas at startup. Keep `runtime/fonts` beside the executable when Chinese is included. Japanese and imported English use their own original font assets. This changes source memory use, not glyphs, layout, resolution or GPU texture sizes.

If a build is interrupted, keep the unchanged checkout and completed outputs, then use:

```bat
build.cmd --iso "D:\Games\Shin Megami Tensei - Nine (Japan).iso" --resume
```

Include `--with-chinese` again when resuming a Chinese-enabled build. The language selection is recorded in `build/progress.json`; changing it during resume fails explicitly. Completed phases are reused only after their recorded output hashes match. A failed phase is not marked complete. Do not use this continuation option to reuse outputs after changing source or translation inputs, or to resume a build created before this selection was recorded. Use a fresh checkout to change the initial language selection. For program updates after a successful build, use `update.cmd` (equivalent to `build.cmd --update`); see the README for source and compiled-play update commands. It verifies and retains installed Media/font outputs. Chinese-enabled updates rebuild the Chinese runtime image from the current fixed-field translation inputs; Japanese-only updates reuse their image. Changes to Media/font translations require a separate full build. Imported language build directories must remain available for their host updates.

`build/completion.json` records the actual ISO checksum or source-directory path, tool paths, duration and executable identities. Folder resumes require the same directory and recheck its complete original contents; ISO resumes require the same input checksum. Program updates use the installed verified resources without the original input. Build completion is separate from game-flow validation.

Only original Japanese game files and their source fragments have fixed hash requirements. GPU archives, GPU DLLs, generated function bodies and translated outputs are not compared against hard-coded hashes. Build receipts, checkpoint identities and release manifests describe the actual build or release and retain their dynamic integrity checks. Project code-generation edits check the targeted text and its context before applying changes.

GPU dependencies enter `build/downloads` only after the archive is readable, required DLLs are present, and their x64 PE structures are valid. The D3D11 DXGI import is located through the PE import table and renamed in place, without a fixed file offset. Failed new downloads are discarded. A changed upstream archive is accepted when these structural requirements hold; this does not establish gameplay compatibility with every upstream revision.

If a download fails in the build but works in your browser, use the direct URL shown in the error and save the archive, **without extracting it**, at the cache path shown there. For WineD3D, the path is `build/downloads/wined3d.zip`. The [WineD3D direct download](https://downloads.fdossena.com/Projects/WineD3D/Builds/WineD3DForWindows_11.19-x86_64.zip) is the same URL used by the build. Replace an invalid cached file with the working browser download, then rerun the initial-build command with `--resume`, keeping the same input and `--with-chinese` selection. For a program-only update, rerun `update.cmd`. The cache is checked structurally and reused; no automatic source switching is performed.

## Compiler profiling for maintainers

Ordinary builds use `SMT9_PROFILE_MODE=Off` and need no training data. For an MSVC Release build, configure the existing CMake directory with `SMT9_PROFILE_MODE=Generate` to produce a training executable. Run it from the x64 Visual Studio developer environment so the compiler's profiling runtime is available, and exercise representative game scenes. Use Microsoft's [pgosweep](https://learn.microsoft.com/en-us/cpp/build/pgosweep) with the actual process ID to collect counts before closing a test process.

`SMT9_PROFILE_DATA` names that build's profile database; it defaults to `smt9_recomp.pgd` inside the CMake build directory. Keep the corresponding numbered `.pgc` files beside it. Configure `SMT9_PROFILE_MODE=Use` and rebuild the same game target to produce the optimized executable. Profiles belong to the matching compiler, sources and language build; they are build artifacts, not player resources. The training executable collects counters and is not the finished optimized program.

`SMT9_LINK_TIME_OPTIMIZATION=OFF` explicitly selects ordinary separate compilation for a controlled comparison and cannot be combined with profile generation or use. Profile-guided builds require MSVC. These options affect native compilation, not game frame pacing, rendering quality, save formats or the Config graphics-processing setting. Compare optimized builds on the same save and route; training-run timings are not performance results.

## Languages

Config lists Japanese after the default build, and additionally Chinese with `--with-chinese`. Interface language (Chinese/Japanese/English) and game language are independent. Selecting an unavailable Chinese game through a manually edited INI fails explicitly; it does not change the selected language automatically.

For an external English translation, first apply that translation's patch to your own ISO. Open Config and choose **Import or update language ISO…**. Use identifier `English`, display name `English`, and select the already-patched ISO. The importer extracts its complete assets and recompiles only the changed functions using the existing local generated baseline. To replace an installed translation, select the newly patched ISO and keep the same language identifier (`English`); there is no fixed translated-ISO checksum lock. A successful build switches that identifier to the new package, without adding another language entry. Settings and shared ordinary saves are kept; instant states still require their original executable and image. An unsuccessful update leaves the previously registered package intact.

The initial Japanese build is required before language import; Chinese is not required. Imported executables inherit `SMT9_WITH_CHINESE` from the base build's existing CMake cache. The project does not download, distribute or apply the English translation patch. A translation that changes the unsupported executable layout fails explicitly and requires integration of its changes.

## Local files

`runtime/NINE.ini` stores display/interface settings and the keyboard/gamepad bindings configured in Config. Existing INIs without binding sections retain the original default profile. Invalid bindings produce an explicit configuration error; they are not silently replaced. Imported packages and their logs live under `runtime/languages`. Screenshots are under `runtime/Screenshots`. Ordinary user data is shared by all languages through the existing host path mapping; imported caches remain isolated by package. Instant states are valid only for the exact executable/image that created them. Do not commit or distribute any of these files.

Ordinary saves live under the root `save/UDATA` and are shared by Japanese, Chinese and imported languages. Back up the entire `save` folder; Config → Save folder opens it. Instant slots live in `save/states/<language>` and still require their exact executable and game image. They are not interchangeable between languages or program builds.

When `save` is absent, the game or Config copies the old ordinary saves from `data/chinese/UDATA`, `data/chinese/TDATA` and `runtime/save/UserData`, keeping the originals. Old instant states are archived under `save/states/legacy-built-in` and `save/states/legacy-imports`; archiving does not convert them for a new executable. Once `save` exists, it is authoritative and old files are not reimported. `runtime/save` contains disposable runtime caches and is not the ordinary save folder. Program updates preserve `save` and never include player saves.

PC storage uses ordinary directories. Utility-drive startup selects the existing cache directory, validates it through the existing volume API and registers the original drive alias. It does not read or format raw Xbox partitions and does not create `Partition*.img` files. Imported languages retain their separate cache directories.

## Compiled program updates

Place `Updater.exe` beside `smt9_recomp.exe` and open it. The updater follows the saved Config interface language (Chinese, Japanese or English) in `runtime/NINE.ini`, independently of the game language and Windows display language. Save the interface setting in Config and reopen the updater to use it. Without a saved setting, it uses Config's build default: English for Japanese-only installations and Chinese for Chinese-enabled installations. It checks the latest stable GitHub release, selects the Japanese-only or Japanese/Chinese package from the installed game images, verifies the download against both the release asset digest and `SHA256SUMS.txt`, and shows how many files differ. Close the game and Config, then choose **Update now**. Checks and downloads run in a separate process so the window stays responsive. Failed downloads or incompatible packages produce an error without applying files; the user can check again. File comparisons also detect changed attachments under the same release tag. The updater uses Windows PowerShell and .NET supplied with Windows; Python and build tools are unnecessary for compiled program updates.

The update ZIPs contain the appropriate native executable, Config, Updater, license text and update scripts. The Japanese/Chinese package also carries the Chinese runtime image for text corrections. The Japanese-only package does not include it, and Updater selects that package when Chinese is not installed. Neither package contains original Media, fonts, the Japanese game image, ISO, settings or saves. Manual installation still uses `Apply-Update.cmd` or `Apply-Update.ps1 -Target`. Both interfaces use the same installer: it checks every payload and the unchanged Japanese image, confirms Chinese is already installed for a Chinese update, then copies changed files, rejects the wrong language variant, and skips identical files. `Apply-Update.ps1 -CheckOnly` performs verification and reports pending file counts without writing. A full first build still requires the player's disc. The graphical updater updates compiled Japanese/Chinese programs; source code and imported translated hosts use `git pull` and the source directory's `update.cmd`. Source updates regenerate each installed translation's changed functions against the current generated baseline, using its retained native image, before rebuilding. Original language assets are reused; the translation ISO is not required again.

Chinese source updates reuse the original Japanese files and existing Media/font outputs, then rebuild the Chinese runtime image with the current fixed-field translations before code generation. HP, MP and combined HP/MP full-recovery labels use “全回复”. Updater.exe itself does not need replacement for these resource updates.
