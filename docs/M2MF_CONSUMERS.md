# NV039 memory-to-memory consumer

The existing class39 object, RAMHT lookup and PFIFO puller remain authoritative. Context methods180/184/188 retain the resolved notifier/source/destination DMA instances. Methods30C..324 retain byte offsets, byte row pitches, byte line length, line count and format in existing PGRAPH class state; the same NV2A checkpoint retains them. The checkpoint state-size contract rejects incompatible layouts.

The established subset accepts format0x101, nonzero positive pitches no greater than0x7fff, line bytes smaller than0x400000, one to2047 lines, and non-overlapping source/destination spans with line length no greater than either pitch. Each whole DMA span and the mandatory notifier record are validated before any copy. Trigger0 copies rows in the existing mapped RAM, then writes notifier DMA+0x10. This uses the original nv_dma_span resolver and ptimer_get_clock; no second DMA or copy pipeline is introduced.

The16-byte record receives the current PTIMER high/low timestamp, zero information at+8 and zero completion at+C. The completion word uses the existing platform InterlockedExchange primitive, publishing prior RAM and record writes before a polling consumer sees completion. Trigger0 does not request an interrupt. The timestamp is the original exposed PTIMER TIME register pair, equivalent to its existing clock shifted left5.

Other format increments, buffer-awaken trigger1, overlapping/zero layouts, incomplete state and hardware error/partial-copy completion are not supplied by a substitute. They retain explicit stops. The same class0039 Linux producer demonstrates the accepted format101 positive-pitch packet; NVIDIA defines class fields, and envytools documents the mandatory M2MF record. The inspected original game initialization establishes class39 handleE and DMA binding, but no original operational submission has been established. This is not a whole-title or arbitrary NV039 completion claim.

The original GPU fixture submits real RAMHT/class39/DMA FIFO packets and checks padded byte rows,2047 lines, inclusive DMA end, checkpoint restoration, all destination bytes and untouched guards. A notifier aliasing the source confirms copying precedes record writes. An existing-thread observer waits for the completion word and then checks copied RAM and record information. Timestamp bytes are bounded by the same real clock. Unsupported increments/buffer-awaken/overlap stop. Restoring the original core causes the same legal packet to stop at30C; that negative control is retained.

Ordinary method104 follows the established generic NV4+ graph-object contract independently of buffer trigger328. Values0 and1 arm one pending request for the bound class39 object/subchannel. The next graph method completes before slot0 is written using the same validated DMA/PTIMER/record primitive. Value1 then asserts the existing ordinary NOTIFY interrupt bit0 through nv2a_update_irq. Buffer slot+10 is untouched. The pending/type/subchannel/object identity live in the original class state and checkpoint. A second104, DMA-notifier change, object binding or subchannel switch while pending stops, as does parameter>1. Negative pitches retain the independently tested NV20 method rejection (valid range0..7fff), rather than extrapolating a signed API typedef into hardware legality.

The ordinary-notify fixture submits original RAMHT/FIFO packets, verifies104 itself leaves RAM/IRQ untouched, restores a pending request through the existing checkpoint, and checks record bytes plus the live IRQ callback after NOP completion. The callback observes the completed record and ordinary bit0; buffer bit16 and buffer record stay untouched. Original-core negative control stops at104. The old103000-byte NV2A register layout is still rejected inside XBGPUR before apply; the expanded state now has48 added bytes.

FORMAT setup accepts the original NV20 nine input/output increment combinations1,2,4 with reserved bits rejected. These are state identities confirmed by the independent hardware method test, so a legal temporary setup does not stop merely because a later trigger would require unimplemented copy semantics. Operational trigger328 still accepts only0x101 and stops for other increments; accepting setup is not a substitute for gather/scatter execution. The original NVIDIA interface establishes byte units for offsets, row pitches and line length. What remains unresolved is how increments control useful-byte width versus skipped bytes, and how a partial final unit is handled; the method-state test disables actual DMA and does not establish those outputs. The legal RAMHT/FIFO setup fixture checks all nine exact stored values, unchanged RAM/IRQ, and five invalid bit/value cases. The pre-setup core negative control stops on legal0x201. A separate0x202 transfer still stops at its trigger.
