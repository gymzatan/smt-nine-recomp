# NV09F logical blit consumer

The original class43 ROP producer writes its method300 low byte to the NV20 PGRAPH ROP register at offsetB00. Existing NV09F context190 names that object. NV09F operation1 (ROP_AND) consumes it through the established surfaces/DMA/clip/row-copy path. PGRAPH retains the register in its existing checkpoint; no register-state structure or buffer ABI was enlarged.

The confirmed subset uses X8R8G8B8, NULL chroma/pattern contexts, pattern-independent ROP3 and disjoint spans or identical physical pixel starts with equal row pitches. ROP CC additionally accepts same-pitch linear shifted overlap through the original SRCCOPY row consumer; spans intersecting active physical tiles are excluded. NULL pattern is an explicit original context disable: the NV20 method model accepts expected class or NV_NULL and clears context-cache bit27 for NULL. Restricting ROP3 to equal upper/lower nibbles removes any dependency on undefined pattern bits. X8 pixels have opaque alpha under the already accepted surface-format contract; raw source high bytes0,1,127,128,255 therefore do not act as an alpha discard mask. Existing destination opaque-alpha fixup remains authoritative.

ROP3 indexes each truth bit by(P,S,D). For the sixteen pattern-independent functions, reversing the low nibble bits gives the existing GL logic-operation index. The original color_logic function was moved verbatim to one nv2a header with staticinline linkage; its kernel caller remains unchanged. Core invokes that same function after opcode mapping. There is no second truth table, pixel interpreter or core-to-kernel dependency.

The original RAM fixture checks all sixteen functions against independent absolute results, five source high-byte values, two pitched rows, every destination byte and padding guards. It also checks ROP register checkpoint restoration through the existing NV2A snapshot. The accepted software fragment logic matrix and original NULL-context blit remain passing. The original core fails the same valid class43 method300 input; the negative control and exact shared-function extraction hash are retained.

Nonempty key/pattern, alpha-bearing source formats, pattern-dependent ROP, shifted overlap outside the ordinary same-pitch linear ROP CC subset and partial-pixel tile completion retain explicit stops. Existing accepted physical-span clipping is reused; no physical tile encoding, consecutive-tile or unknown overlap order is supplied. Original title construction/binding evidence is reused without claiming this operation has been observed in gameplay.

Ordinary source-copy overlap uses resolved physical RAM identities, including distinct DMA handles mapping the same memory. A higher overlapping destination is visited from the last row; horizontal overlap stays in the original memmove, with the existing opaque-alpha fixup after copying. This preserves the pre-operation source rectangle without allocating an image snapshot. The Haiku NVIDIA accelerant uses class009F/0062 with ROP CC for screen moves and scrolling and assigns direction selection to hardware. The actual original GPU fixture checks 70 moves, format and DMA-alias combinations against pre-operation RAM, including all padding guards. Cross-pitch, physical tile and non-CC ordering are not generalized from this contract.

ROP context identities select the pipeline context enable/class; they do not restore per-object ROP values. The original hardware method model writes the single ROP register, and contextROP binding only validates class43/NV_NULL and updates context bit28. The primary2D overview explicitly describes one pipeline state copy and distinguishes aliasing from software-managed swapping. Thus within one channel, A writes66, B writesCC, rebinding/referring to A still consumes globalCC unless software explicitly writes66 again. The dedicated actual RAM case yieldsFF69CC33 forCC, thenFFAA3C3C after an explicit66 write, with source9669CC33/destination3CC3F00F. No per-object shadow was added. Software-managed invalid contexts/swapping are not inferred from this aliasing case.

SRCCOPY_AND operation0 is also connected for the same opaqueX8, NULLkey/pattern, complete-pixel subset with disjoint spans or identical physical pixel starts and equal row pitches. The original operation contract is source copy with zero-alpha discard; the accepted X8 source conversion makes alpha opaque, so that discard never fires and the original copy/opaque-alpha fixup path is the exact consumer. This is an explicit operation0 connection, not substitution for unknown operations. Raw source high bytes0,1,127,128,255 yield the same converted opaque pixels. Alpha-bearing formats and nonempty pattern/key remain outside this established subset. The current pixel/row/limit checks are preserved, and unsupported overlap/partial-pixel cases stop before writing.

The operation0 fixture checks distinctRGBpixels in two pitched rows, all256destinationbytes/guards and five raw source high bytes. The originalROP1 fixture is retained as the adjacent-path regression. Restoring the previous core causes the identical legal operation0 SIZE packet to stop at0308; the negative control is preserved.
